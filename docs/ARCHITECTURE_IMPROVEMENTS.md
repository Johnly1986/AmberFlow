# 新架构改进意见（结构、接口、缝——不是再调几个阈值）

> 来源：本轮独立复核（[docs/DECISION_MODEL_PURPOSE_REVIEW.md](DECISION_MODEL_PURPOSE_REVIEW.md)）+
> 四个视角的子代理审查（简化配置 / 弹性容错 / 文档一致性 / 红队）收敛出的结论。
> 与已有两份文档的关系：**[MODEL_ROLE_PLAN.md](MODEL_ROLE_PLAN.md)** 管"模型该站哪"、
> **[MODEL_ROLE_IMPL_PLAN.md](MODEL_ROLE_IMPL_PLAN.md)** 管"那件事怎么落地（W1–W5）"；
> 本文管**架构本身**——那些不改就会持续复发的问题。
>
> 每条：**问题（带数字）→ 改什么 → 为什么是结构问题而不是调参 → 验收判据 → 代价/风险 → 边界**。
> 排序按"性价比 × 复发频率"，不按"看起来高级"。

## 0. 一句话

这版架构在**能力**上已经够了（声明 + 规则 + 编译/录制承重，模型兜底），
但它有两个**结构性弱点**：**数字没有单一出处**（同一个数抄在多处，本轮一次复核就抓到 7 处过期）
和**缝是隐式的**（决策接口把两个不可比的量塞进一个 `conf`；运行策略只能由命令行给、包作者声明不了；
"危险"是一个布尔而不是可逆性模型）。改进的重心应该在这三处缝上，而不是继续加声明面。

## 1. 计量要有单一出处（P0，零行为风险）——**已落地**

**问题**：同一份仓库里，同一个数有多个版本。本轮实测到的：测试条数 **1061（图）/ 873（CLAUDE.md）/ 1068（枚举）**；
`bindings` 条数 **17 / 20**；语料步数 **180 / 190 / 191 / 192**；"机械行" **61%（15 包时代）/ 60.9% 或 57.1%（今天，取决于数法）**；
脚本桩基线 **~240 s（估计）/ 160.7 s（实测）**；"0 代码行"里藏着 `bin/` 的 **101 行**；
`when/retries/next` 的 **7/12/1 与 8/17/1**（分母不同）。**它们不是笔误，是同一个数被抄在多处。**

**改什么**（本轮已完成第一步）：
- `tools/arch-metrics.ts`：把能算的全算出来（语料结构、hint 覆盖、声明覆盖的**三套分母**、行数、`bin/` 夹具行数），
  把算不出来的**标明来源**（测试条数必须来自 `npx vitest list`——静态数 `it(` 只有 799，不可用；
  模型段来自 /tmp 的跑批产物，换机器就是另一批），写进 **`docs/arch-metrics.json`**（单一出处）。
- `npm run metrics`（`--check` 只比**仓库能算出来的 `corpus` 段**，model/tests 两段是快照，不参与门）。
- **下一步（未做）**：两个架构图生成器**从这份 JSON 读数字**，而不是把 `1068` 写在字符串里；
  这样"图里的数过期"会直接被 `--check` 挡下（今天挡不下——`--check` 是自洽门，图里写 1061 也照样绿）。

**为什么是结构问题**：只要数字是"抄"的，下一次复核还会抓到 7 处；只有让它们"算"出来，这类缺陷才会消失。

**验收**：`npm run metrics --check` 绿；两个生成器读 `docs/arch-metrics.json`；改一个 pack 后不刷新 JSON ⇒ 门红。
**代价/风险**：S；零行为风险。**边界**：`model`/`tests` 两段永远是快照（依赖本机产物），只能在文档里标明"何时、何命令测的"。

> **状态（本轮）**：✅ 工具 + JSON + 两个生成器接上（v1/v2 的测试数、hint 覆盖率、top-1、precision、
> 两支 AUC、采纳/对数、真模型出场数全部改为插值）。**真值门实测有效**：把 JSON 里的 `tests.count`
> 改成 9999 ⇒ 两个 `--check` 同时 exit 1；改回即绿。JSON 缺失/缺字段也记为问题（先检查后写，不落坏图）。

## 2. 决策接口要按"问法"版本化（P1，解 W4 的阻塞）

**问题**：`pickElement` 返回的 `conf` 是**两个不可比的量**：池 ≤ 8 时 `1 − 归一化熵`（在全部选项上算），
池 > 8 时短名单重问的 `max(probs)`。合并看是 AUC **0.325**；拆开看是 passthrough **0.233（反向）**
与 shortlist **0.587**。闸门却拿同一个 `floor` 比它。更直接的后果：W4 的停止条件写的是
"两栏 AUC ≥ 0.5 且 precision 高于现状"，而 `tools/model-contribution.ts` 的产物行里**只有 `conf`**，
没有 `p(top1)`/`margin` ⇒ **现成产物回答不了计划自己的停止条件**（复核实测）。

**改什么**：把"一个 float"换成**带问法描述的结构**：
```
Proposal = { choiceRef, shape: {kind: "full" | "shortlist" | "narrow", k, poolSize},
             pTop1, pTop2, margin, entropyConf,  // entropyConf 降级为诊断，不再当闸门输入
             modelId, checkpoint, version }
```
闸门策略按 `shape` 分档读取（`gate: {full: ..., shortlist: ..., narrow: ...}`），
报告与 trace 记 `shape`；`tools/model-contribution.ts` 落 `pTop1/pTop2/margin`。

**为什么是结构问题**：现在的缝把"模型的不确定性"压成一个标量，**信息在函数返回时就丢了**——
下游无论怎么写阈值都只能用一个尺度去量两种问题。这不是调参能修的。

**验收**：`model:contribution` 的产物含 `margin`/`pTop1`；两支的 AUC 与 floor 曲线**直接从产物算得出来**；
六层对拍与 `apps:suite` 默认档逐字节不变。
**代价/风险**：M；改的是 `LayaRuntime` 的返回结构与闸门读取点（默认档行为不变）。**边界**：`narrow`（tieredHint）默认关，只增不启。

## 3. 运行策略要能声明（P2）

**问题**：`tieredHint`（窄问）是 `RunOptions` / CLI flag / DSH 桥的参数——**包作者无法为自己的包声明它**
（`PACK_KEYS`/`STEP_KEYS` 里没有这个键）。于是"这个应用适合窄问"这条知识只存在于跑命令的人脑子里，
报告里也看不到"这次跑用了什么策略"。

**改什么**：给包加一个**声明式 policy 块**（`pack.policy`）：`gate` 档位、`narrowAsk`、`reobserve` 次数、
`riskAsk` 策略、`maxSteps`…；缺省 = 今天的行为（逐字节不变）；CLI/桥的显式参数**只覆盖本次运行**；
报告打印 `effective policy` 与它的来源（包 / CLI / 缺省）。

**为什么是结构问题**：现在配置面被劈成两半——"应用是什么"在包里，"这次怎么跑"在命令行里——
而**可复现性要求后者也能进包**（否则同一个包含义随命令行变，`apps:suite` 与真机跑的不是同一件事）。

**验收**：同一份 pack 在两个不同 policy 下产出**可解释的差异**（报告里有 policy 段与来源）；
不声明 policy 的包输出逐字节不变；`apps:matrix` 增一列 `policy`。
**代价/风险**：M；风险 = 又加一层声明（**与"简化配置"反向**）⇒ 因此只允许**包级**、不允许逐步写；
逐步开关要继续留在"默认关、由包级打开"的层级里。

## 4. 可逆性模型：把 `dangerous: true` 换成 `effect`（P2）

**问题**：今天安全边界是一个布尔。A2（"只在页面能拒绝的步放开模型"）的真实覆盖面因此被压得很窄：
按实测元素标签，语料里 `select` **40.1%** + `input` **9.9%** = **50% 是非破坏性的**，
但**真正会被页面校验拒掉的只有 `input` 那 9.9%**——`select` 选错页面照收，只是信号不成立、这步白跑。

**改什么**：把步声明从 `dangerous: bool` 升级为 `effect: { irreversible?: bool, undo?: <step ref> }`，
执行器在动作后**校验**（信号 + 值变化），不成立时若声明了 `undo` 就回退，并记 `adjudicated_rejected` / `rolled_back`。
模型只在 `irreversible !== true` 的步上被允许提议。

**为什么是结构问题**："能不能让模型试"取决于**这个动作错了会留下什么**，而"危险"这个词把
可逆（选错下拉、填错表单）与不可逆（提交订单）混成一个布尔，于是策略只能一刀切在最保守的一侧。

**验收**：`camera-entry` 删掉 hint 后从 0/4 → 能走完（页面校验 + 信号）；"错误动作被采纳"= 0；
不可逆步声明 `undo` 在加载期报错；负例测试覆盖"选错下拉 ⇒ 白跑但不误报成功"。
**代价/风险**：M–L；风险 = 回退动作本身可能有副作用 ⇒ `undo` 只允许引用**声明过的、非危险的**步。

## 5. 梯级卫生：没出场的梯级要有数字（P1，报告即可）——**已落地**

**问题**：决策梯级有 5 级（规则 → hint → laya → 加宽重看 → 升级老师），而实测里
**`reobserve` 与 `escalate` 在已验收语料上救回 0 次**（两个模型层级都是 0；真模型语料 5 次咨询、0 次过关）。
"梯级存在"与"梯级有用"是两件事，而报告里只有出场次数，没有**救回次数**。

**改什么**：报告与 `apps:suite`/`matrix` 增一行**梯级账单**：每级的 `出场 / 过关 / 救回`
（定义"救回" = 该级决定的那一步，若换成规则/hint 会 blocked 而它 done）。
任何一级在**整个语料**上 `救回 = 0`，报告打 `dead rung` 并在文档里二选一：**接线**（例如 escalate 接端点）
或**删除**（把死重从架构里拿掉）。

**为什么是结构问题**：一个从不救回的梯级不是"保险"，它让人以为有兜底（红队原话：**"全绿"从定义上不经过真模型**），
还会按每步一次前向收费（597 s vs 160.7 s 的主要来源是风险头）。

**验收**：报告出现梯级账单；`escalate`/`reobserve` 的 0 救回被明示（不是"未测"）。
**代价/风险**：S；只读统计，无行为风险。**边界**：`reobserve` 在 `tests/reobserve.test.ts` 里是有救回案例的
（60 个诱饵按钮那种），所以"0"只在**已验收语料**口径下成立——这正是要写清的口径。

> **状态（本轮）**：✅ `AppDecisions.ladder`（与 `by_method` 对账，不自造数）+ 套件页脚梯级账单。
> 本轮实跑输出：**`规则/hint 决定 201 ｜ laya 0 ｜ reobserve 0 ｜ escalate 0 ⇒ dead rung：laya、reobserve、escalate`**。
> 回归钉在 `tests/ladder-bill.test.ts`（单独文件：`suite()` 会装自己的计数缝，放同文件会把邻居测试的咨询数顶成 0——踩过）。

## 6. 声明面的归并与编译入口（P3，最贵也最根本）

**问题**：新声明面是**纯加法**：`git diff` 显示 `apps/` 只有 `+136/−0`——0 个既有包被改写或删除。
同一个意图现在有**三条写法**（拆步 + URL 深链 / `target_hints` / `commands`），
`target_hints` 已在 5 包/22 步表达"填→提交"，而 `commands` 是第二条并存路径；
`commands` 在语料里只用在 2 包/4 条。第一次重审就写过"候选列表不由人手写，由编译器枚举"——
今天仍没有"从意图编译"的入口（`apps:gen` 只覆盖 8 个由 spec 生成的包）。

**改什么**：定义**每种意图的唯一规范写法**，并把历史写法标成可迁移的旧式：
- 一个 `compileIntent(goal | spec) → plan` 入口，现有声明面（`commands`/`bindings`/`next`/`target_hints`）
  作为它的**输出目标**而不是"第三种手写方式"；
- 迁移报告：哪些包用了旧式，编译后是否等价（用现有的零模型回放门判定）；
- 新能力**默认不新增语法**：先问"这条意图现有面能不能表达"，能就进编译器。

**为什么是结构问题**：声明面只增不减 ⇒ 作者要同时懂三套写法、读图成本上升、覆盖面统计失真
（"98.8% 的步点名目标"里有多少是编译器产的、多少是人写的，今天分不清）。

**验收**：三条写法收敛到 ≤2；新包默认走编译入口；`apps:matrix` 增"写法来源"列；
迁移后的包零模型回放全绿（既有门槛，不许放松）。
**代价/风险**：L；风险 = 大范围改冻结语料 ⇒ 所以**只对新包强制**，旧包按迁移报告逐个来，冻结语料不动。

## 7. 弹性要有"族"而不是"一次 A/B"（P2，与 W3 同源）

**问题**：今天证明"声明在承重"的那次实验（删掉全部 hint → 4/4 → 0/4）是**临时 A/B**；
仓库里没有任何门禁会在"页面漂移"时给信号。红队补了一刀：即便按计划走完，**弹性也没有一个被保证会绿的验收台**
（W3 给的是一张"今天必须红"的记账夹具，绿要等 W4，而 W4 自带一条允许取消的停止条件）。

**改什么**：把 W3 扩成**漂移族**（每类一个夹具 + 一个声明过的期望）：
① 改 `id`／② 加一层 wrapper／③ `button`→`a`／④ 文案改写／⑤ 桌面 DOM 换成移动 DOM（`pack.device` 那一类）。
每类给出**恢复率**（哪一级救回、代价几步），并要求：`模型边际 = 0` 时 CI 不许显示为通过（红队的最小修正）。

**为什么是结构问题**：弹性不是一个可以"声称"的属性，而是**一族必须逐类计价的行为**；
没有分类，就只能拿一句"我们有兜底"当结论。

**验收**：5 类夹具进 CI；每类有 `恢复率/代价` 数字；恢复率为 0 的类别在文档里写明"不承诺"。
**代价/风险**：M；风险 = 夹具人造 ⇒ 每类都要写清"代表真实世界里的哪种改动"。

## 8. 图与文档的"真值门"（P0 的一部分）——**已落地**

**问题**：两个生成器的 `--check` 是**自洽门**（图 == 生成器输出），不是真值门：图里写 `1061` 而实际 `1068`，
`--check` 照样绿。文档侧同理——散文里的数字没有任何门盯着。

**改什么**：① 生成器从 `docs/arch-metrics.json` 读数字（见 §1 下一步）；
② 文档里凡出现"可算的数"就写成 `npm run metrics` 的口径（不写裸数字）；
③ 在 `ARCHITECTURE.md` 顶部点明**哪张图是规范**（六层总览 = 现状，目标图 = 现状 + 裁定 + 下一步），
避免同一件事两套讲法各说各话。

**验收**：故意把 JSON 里的测试数改错 ⇒ 两个 `--check` 至少有一个红；`ARCHITECTURE.md` 有"规范图"声明。
**代价/风险**：S。

> **状态（本轮）**：✅ 前半（改 `tests.count=9999` ⇒ v1/v2 两个 `--check` 都 exit 1，实测）。
> 后半（哪张图是规范）见下方 §8b。

## 9. 不要做的（反清单，与上面同等重要）

- **不要**整体降 floor / 扩大 shortlist k / 把 hint 变成可选：数据已否（净增 47 个错误、只多 19 个正确）。
- **不要**为了"让模型承重"而加声明面：那正好把"简化配置"再推反一次。
- **不要**把 1.7 GB 权重塞进 CI：CI 跑脚本桩，但"CI 绿 ≠ 模型有用"必须写在文档里（红队要求）。
- **不要**用"每个步写一个开关"的方式落地 A2：逐步开关只能由包级 policy 打开（§3）。
- **不要**在没有 `model 边际` 这个数之前宣布"弹性/容错达成"：今天那个数是 **0**。
