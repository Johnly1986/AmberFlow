# 审查意见 A — 产品视角

角色设定：你是一个开发者工具的产品负责人，负责把 AmberFlow 推给多种 Harness 的
Agent 用户。审查对象是 docs/PROMPT_SYSTEM.md 提出的三层提示词系统设计。

审查维度（逐项给出 通过 / 有保留 / 不通过 + 理由 + 修改建议）：

1. **上手路径完整性**：一个从未接触过本仓库的 Agent，只通过层 1 的索引命中，
   能否在 3 次工具调用内发出第一条正确命令？概述里"从哪开始"是否闭环？
2. **三层职责边界**：概述层会不会塞进了工具层的内容（命令参数细节）？
   工具层会不会塞进了提示层的内容（失败排查）？每层是否只回答自己那类问题？
3. **维护成本与单一出处的张力**：新增一个投放面（比如又一个 harness 的入口
   文件）时，设计是否保证不需要同时改两处文案？校验层的数量是否在膨胀，
   有没有更好的收敛方式？
4. **信息密度控制**：概述文本的长度预算（索引命中时往往只有几百 token 的
   展示空间）；help 输出的长度预算（太长会稀释关键信息）。设计里有没有
   明确的分层长度约束？
5. **与既有文档的关系**：README / AGENTS.md / ARCHITECTURE.md / 各 docs 是否
   出现了职责重叠或互相矛盾的风险？PROMPT_SYSTEM.md 自身的定位是否清晰？
6. **可验收性**：方案的目标（提高维护性、统一来源、提高上手与规划效率）
   是否各自有可验证的判据？实施后怎么知道"成了"？

输出格式：每维度一段，最后给出【必须修改项】清单（按优先级排序）与
【可选优化项】清单。审查必须基于文档原文，不得虚构文档没有的内容。
