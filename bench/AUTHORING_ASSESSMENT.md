# 现状评估：这 18 个应用里，多少是"机器本该生成"的？

**触发这个评估的判断**：「正常很少有用户回去手写流程。」——之前一轮我把力气花在"教你手写 `pack.json`"
（README 的最小包样例、`target_hint` 报错文案），很可能是在服务一个基本不存在的用户。

下面是**测量**结果，不是估计。方法：只读遍历 `apps/*/pack.json`（15 个），按顶层键统计源码行；
对每个有 spec 的应用，把它展开后的计划与 `emitPlan(<spec>)` **逐字段**比对（`desc / start_url /
target_hint(s) / signal / when / retries / slots`；`start_url` 按仓库相对 ↔ `file://` 归一化，
这是包里本来就有的写法差别）。

## 一、一句话结论

**15 个有旅程的应用共 2965 行声明，其中 61%（1797 行）是"某个已存在数据展开一下就能得到"的机械内容；
真正必须人写的判断只有约 31 条**（29 条结束态不变量 + 1 个设备声明 + 1 个危险动作声明）**，
外加 281 行线上**测量**数据（探针集）。手写那 61% 换来的不是准确率，而是 7 轮"作者写 + 复核方逐字段验"
的流程成本——因为我们自己的复核证明它抄得对（0 diff），这恰恰说明它不该由人来抄。

## 三、三层分类（这才是可执行的结论）

**第 1 层｜由构造生成，0 判断（1197 行 / 7 个应用）**
`transfer-skybook / flyquest / trekly / farehaven / voyagio / slowjet` + `ctrip-case`
——上游是 `transfer/specs/*.json`，`emitPlan()` 已经能展开成计划，包只是它的另一种写法。
**生成器形态**：`spec → pack`，对齐由构造保证（不再需要"对齐测试"，因为它不是两处独立写的东西）。

**第 2 层｜由既有构件生成（约 400 行 / 4 个应用）**

| 应用 | 上游构件 | 还缺什么 |
|---|---|---|
| `ip-config` | `src/ip-config.ts` 的 `PAGES × DEMO_ROWS`（已有 `buildPlan`） | 3 条不变量 + notes |
| `demo-app` | `bench/fixtures/shop_cart.html` 的演示计划 | 2 条不变量 + notes |
| `cli-report` / `repo-report` | `apps/*/sources/*.json`（argv 已经是数据） | 旅程本身（5 / 3 步）+ **危险动作语义** |
| `qunar-live` 的旅程 | 原 `qunar-task.ts` 的冻结计划 | 设备声明 + 5 个探针键 |

这一层里，`sources` 的 argv/URL 模板**已经是数据**；缺的只是"把这些步骤串成旅程"，
而这正好是第 1 层生成器要解决的事（同一种展开器，输入换成 builder 输出）。

**第 3 层｜只能人写：测量或判断（不可约残差）**

| 项目 | 数量 | 为什么不能自动 |
|---|---|---|
| `invariants`（结束态断言） | **29 条** | 需要"什么必须成立"的**意图**。可以**归纳**（`tools/induce_signal.ts` 的假前真后 + 稳定句柄 + 复跑三关），但"这一次的结束态是对的"仍需人/一次成功演示来裁定 |
| `probe` 测量数据 | 281 行（3 个探针集） | 线上事实：门禁页特征 `whaleguard`、登录跳转主机、结果目录。只能**测出来**，不能推出来 |
| `device` | 1（qunar-live） | "这个站点只有手机版"——可由测量发现（桌面 DOM 缺目标），但结论要人确认 |
| `dangerous` / `idempotent` / `dry_run_args` | 1 个危险步 | 语义判断：这条命令**不可逆**。argv 里没有这个信息 |
| `notes` | 143 行 | 人写给人的说明（本轮就出过一次漂移：farehaven 的"3 done + 2 skipped"实测是 1 + 4） |

**注意 `hosts` 不在这张表里**：18 个 host 全部可以从该应用真正用到的 URL 里**提取**出来
（加载期本来就用它做门禁输入），属于"该自动生成却写了两遍"的东西。

## 四、手写换来的实际代价（本次会话的证据）

1. **7 个应用 = 7 轮"作者写 + 复核方逐字段验"**。复核结论逐条是 confirmed / 0 diff——流程是对的，
   但它证明的是**抄写正确**，而不是**这个应用有价值**。
2. **契约不一致的修复成本落在共享层**：手工转写期间，`when` 从来没被校验（第 3 轮 G-M）、
   重试计数跨运行持久（第 2 轮 G-K）——都是"人写的数据没人验"的那一侧出血。
3. **人写的说明会漂移**：farehaven 的 notes 先按 `promoDates`（3 天）写成"3 done + 2 skipped"，
   实测是 **1 done + 4 skipped**（站点用会话级标记）。数据没错，**描述错了**。
4. **"防泄漏门禁"已经替我们证明共享层能被机器检查**：连我写的一句 UX 文案里的裸词 `git`
   都被它抓出来（本轮 §12.0）。**同一套纪律还没有施加在"人写的 pack"上**——
   pack 里唯一被机器强制的是一致性（对齐测试），而一致性正是生成器免费给的东西。

## 五、如果按"用户不手写流程"投入，建议的顺序

| 顺序 | 做什么 | 省掉什么 | 要动多少共享层 |
|---|---|---|---|
| 1 | `spec → pack` 生成器（第 1 层，1197 行） | 7 次手抄 + 7 个对齐测试 + 复核轮次；对齐变成构造性质 | 一个 `tools/` 脚本 + 让 `apps:matrix` 认"生成的包"（例如带 `generated_from` 字段） |
| 2 | 把 `buildPlan`/`sources` 也接进同一个展开器（第 2 层，约 400 行） | `ip-config`/`demo-app`/`cli-report`/`repo-report` 的旅程手写 | 同上，扩展输入类型 |
| 3 | **不变量归纳**：跑通一次 → 从结束态提出候选 → 三关过滤 → 人确认（第 3 层的 29 条） | 最大的一块**判断**成本；`induce_signal.ts` 已有全部机件 | 需要"候选不变量 + 确认"的小流程（可以是一条命令） |
| 4 | 探针集"测一次就写下来"（281 行） | 手抄门禁特征/登录跳转 | 探针驱动已经在报告这些字段，只需回写 |

**不该自动化的部分（保持人写）**：`dangerous`/`idempotent` 这类**语义意图**、
"这次结束态是对的吗"的**裁定**、以及站点是否只有手机版的**结论确认**。
把它们自动化会把"人必须负责的部分"藏进生成器里——那比手写更危险。

## 七、这份评估**没有**证明的事（边界）

- 没测"生成器写出来的包是否可读/可 review"（生成物需要人读得懂，否则只是把成本挪了地方）。
- 没测第 2 层展开器的可行性细节（`buildPlan` 的输出形状 vs `emitPlan` 的输出形状是否同构）——
  只确认了"上游构件存在且已经是数据"。
- 不变量归纳只引用了 `tools/induce_signal.ts` 已有的三关机制，**没有实测**"从一次成功跑出的结束态
  能否提出 29 条里的大多数"。
- 第 1 层的 7 个应用里，`ctrip-case` 的上游还有一个额外约束（要与 `src/ctrip-task.ts` 的冻结计划
  逐字段一致），生成器需要同时满足 spec 展开与冻结语料两个来源——**未验证两者是否总是同一个展开**。

## 八、落地记录：第 1 条已实现（`spec → pack` 生成器）

```
npm run apps:gen -- --list / --write / --check      # tools/spec-to-pack.ts
```

- **做法**：从一个 spec 展开出计划，把每一步的 `desc / start_url / signal / target_hint(s) / when /
  retries / slots` 写进 `journey`；**沿用种子包已有的结构**（角色名、哪些字段是"逐实例覆盖"），
  只把**值**换成展开结果；包里记 `generated_from: { spec, plan_sha256 }`。
- **对齐不只是"验过"，而是构造性质**：`--check` = 加载 + 展开 + 与 `emitPlan(spec)` 逐字段比 + 哈希比。
  手改 `journey`、手改角色模板、改了 spec 没重新生成 —— 三种漂移各有回归测试（`tests/spec-to-pack.test.ts`，12 条）。
- **规模**：7 个应用（6 个 transfer 复刻站 + `ctrip-case`）= 声明 1842 行，旅程不再由人抄写；
  `apps:matrix` 新增"来源"列（`生成:<spec>` / `手写`），并汇总"其中由 spec 生成的 7 个"。
- **门禁**：`bench/smoke.sh` 增加 `apps:gen --check`（改 spec 忘了重新生成 → CI 直接红）。
- **没有被自动化的部分（仍然是人的）**：`invariants`（判断）、`notes`、探针测量、`device`、`dangerous`；
  生成器遇到空的 `invariants` 会**明说**"这个应用什么都不验证"，而不是给一个空壳绿。
- **第 10 条**（不改结构）：生成物与手写物只差 provenance 与 notes，7 个包的手写结构（角色名、内联步）
  逐字保留 —— 这也让 13 条既有断言（含复核方的对抗测试）**一条都不用改**。
- **诚实边界**：生成器依赖"种子包"来沿用结构；没有种子时它按 spec 的 role 名归并（`filter_window` →
  `filter-window`），因此**首个**包的命名仍带人的偏好。第 2/3/4 条（`buildPlan`/`sources` 接入、不变量归纳、
  探针回写）还没做。

## 九、落地记录：第 2 条也已实现（builder 输入）

第 1 条只吃 spec。第 2 条把"上游构件"扩展到**代码里的应用级计划**：

- 生成器新增 `--source <模块>#<导出名>`（`generated_from.source`；加载期校验"模块存在 + 形如 `path#fn`"，
  且与 `spec` 二选一）。`--check` 对两种来源一样工作。
- `apps/ip-config` 因此变成生成物：新增 `src/ip-config.ts#buildAppPlan(rows, portal)`，把整张规划表
  拼成一条旅程，并把**两条验收语义写进代码**（以前只写在人抄的 JSON 里）：
  ① 保存成功不只认"已保存"，还要认**回显的是这一行规划的值**（否则"保存了别的值"也算成功）；
  ② 规划表写错的行（第 4 段 > 255）**预期被设备页拒绝**：错误文案 + 被拒的正是规划里那个值 + 没有"已保存"，
     并带上自己的 `slots`（让"被拒的值 = 规划值"有数据出处）。
- 迁移是**无损**的：`buildAppPlan()` 与手写包逐字段 **0 差异**（8 步：desc/start_url/hint/signal/slots），
  生成后包与手写包只差 provenance 与 notes；ip-config 自己的测试 + 应用验收照旧全绿。
- 现在的账：**8 个应用是生成的**（7 个 spec + 1 个 builder），`apps:matrix` 的"来源"列逐个标出。

**边界（没做的）**：`camera-entry`（类型列路由）**没有**搬进 builder —— 它的上游是"Excel 类型列 × 两套表单 ×
行内证据"的路由表，把它改写成 `buildAppPlan` 等于把判断从一处代码挪到另一处，收益是"可生成"，代价是
同一个应用出现两份路由知识；`demo-app` / `cli-report` / `repo-report` 的旅程与工具步语义（`dangerous` /
`idempotent`）属于**语义判断**，按第 3 层的结论仍在人这一侧。

## 十、落地记录：第 3、4 条（不变量归纳 / 探针基线）

**第 3 条（不变量归纳）**：`npm run apps:induce -- --app <id> [--write] [--runs N]`
（`tools/apps-induce.ts`，站在既有的 `induceSignals(before, after)` 上）。

- **对照态的选择是这条工具的关键**，也是第一次就暴露出来的问题：先用"首页"当对照，归纳出来的全是
  页面 UI（城市输入框、搜索按钮、分页按钮……）——它区分的是"首页和结果页不一样"，不是"这条旅程改变了什么"。
  改成**"这条旅程少做最后一步"**之后，候选立刻变成对的东西：`ctrip-case` 归纳出 `[data-test=hotel-recorded]`
  （与手写不变量**同一个节点**，措辞不同：它给"¥300以下的酒店"，人写"已记录"），以及
  `not css_exists(#ledger-table)` 之类"消失了"的事实。
- **三道闸门**：区分性（结束后真、对照态假）、稳定句柄（`data-test`/`id`/`name` + 非波动量）、
  复跑一致（`--runs N` 取交集）。
- **写回会自愈**，而且这件事**被实测证明有必要**：一次演练里归纳提出 4 条，写回后重跑发现
  `not css_exists(#ledger-table)` **不可复现**（该节点是否缺席不稳定）→ 工具撤掉它 → 再跑
  **19/19、不变量 3/3、exit 0**。"归纳提出、重跑裁决"是它敢写回的唯一理由。
- 它**只追加**，人的判断一条不动（有单测钉住）；措辞仍要人 review——归纳给的是观测到的文本，
  不是人的意图。

**第 4 条（探针基线）**：`npm run probes:baseline [--check|--write] [--from <探针结果.json>]`
（`tools/probe-baseline.ts`）。声明的是**输入**（URL / 风控词 / 登录墙特征），基线记的是**测出来的判决**
（`BLOCKED` / `LOGIN_REQUIRED` / `captured` / 计数）。四种探针驱动的结果形状各自抽取（含 qunar 那种
逐行文本），已从已入库的 2026-10-03 复测记录写入三个探针包（ctrip-live 10 项 / ota-live 3 项 / qunar-live 4 项），
并且**进了 `bench/smoke.sh`（2c）**：站点变了、或有人手改包，CI 就会红。只存标量观察，不存 `*_reason`
（叙述留在冻结语料里，别造第二份会漂移的散文）。

**至此四条全部落地**（1 spec→pack、2 builder 输入、3 不变量归纳、4 探针基线）。仍然留在人这一侧的，
正是评估里说的那部分：`dangerous`/`idempotent` 这类**语义意图**、"这次结束态是对的吗"的最终**裁定**、
以及站点是否只有手机版的**结论确认**。
